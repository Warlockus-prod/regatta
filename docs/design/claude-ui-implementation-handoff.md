# Regatta: передача UI/UX в Claude Code

Дата: 2026-09-28. Владелец реализации: Claude. Визуальная проверка и подготовка
графики: Codex. Статус: план для исполнения, не отчёт о завершённом редизайне.

## 1. Задача и порядок работ

Сначала сделать цельное учебное приложение и соответствующую web-версию.
Затем, отдельным решением, довести один игровой эпизод и выбрать технологию
будущего симулятора. Не начинать сейчас перенос на Unreal, переписывание
парусной физики, новый backend или создание большого 3D-мира.

Цель первого этапа: пользователь без объяснений разработчика находит курс,
продолжает свой урок, понимает схему, выполняет проверку, открывает подходящую
практику и возвращается к тому же учебному контексту. Все разделы доступны
через постоянное Меню. Вся работа не должна свестись к отдельному demo-экрану.

Главное правило процесса: один законченный вертикальный срез за раз,
включая состояния, настоящие данные, обе платформы и проверку.
После каждого среза передавать Codex скриншоты и адреса для визуальной приёмки.
Не ждать графику, если можно безопасно продолжать независимую часть работы.
Нельзя считать визуальную приёмку состоявшейся без её фактического результата.

## 5. Визуальное направление и правила вёрстки

Пользователь учится на телефоне короткими сессиями и читает длиннее на ноутбуке.
Ему нужна спокойная, хорошо читаемая поверхность, а море создаёт контекст,
не служит фоном под каждым абзацем. Стиль: тёплая светлая учебная поверхность,
глубокий синий текст, синий акцент, ограниченные морские изображения.
Существующую выбранную тёмную тему не ломать и не переключать молча.

### Токены

- Светлая основа: `#F7F5F0`; песочная поверхность: `#E9DDC7`.
- Основной текст: `#123247`; primary action: `#006EA6`.
- Подтверждение: `#006D70`. Ошибки и предупреждения имеют отдельную семантику.
- Это направление из текущего плана, а не повод расставить raw hex по всем файлам.
  Использовать семантические роли surface/text/action/border/state и проверить
  их контраст в каждой теме. Сохранить совместимость dark-ocean CSS vars.
- Web: текущий Geist / системный sans. Native: системный шрифт и масштабирование.
  Не переносить зависимость от Google Fonts из HTML и Caveat в учебные подписи.
- Основной текст 16-17, межстрочный 24-26; заголовок экрана около 24-28 на телефоне.
  Подписи вторичны, но не микротекст; prose ограничить примерно 65-75ch.
- Базовый шаг отступов 4; поля телефона 20, на самых узких экранах допустимо 16.
- Touch target минимум 44x44, основное действие обычно 48-52 по высоте.
- Радиусы согласовать в токенах: элементы 12-16, большие фото 20-24.
  Не превращать каждую строку в отдельную карточку с тенью.

### Как переносить HTML

1. Разобрать экраны, состояния и повторяющиеся примитивы, а не копировать
   монолитный HTML в один React-компонент.
2. Сохранить визуальный характер и иерархию, адаптировать фиксированные размеры
   под реальные данные, локализацию, safe area и разные устройства.
3. Рамки телефонов, презентационная боковая панель, фальшивая статусная строка,
   демонстрационные кнопки стенда остаются только в review, не в приложении.
4. CSS Modules и существующие компоненты на web. Не подключать новый UI-kit
   ради пары кнопок. Client boundaries только где действительно есть интерактивность.
5. React Native-компоненты на mobile. Не помещать всё приложение или уроки
   в WebView ради быстрого совпадения HTML. Существующие специальные WebView
   радио/симулятора сохраняются до отдельного решения.
6. Flex/Grid и естественный поток. Absolute допустим для hotspot на изображении
   и HUD, но не для координат всех элементов экрана. Не масштабировать страницу
   целиком через transform, не скрывать overflow как лечение сломанной вёрстки.
7. Рабочие кнопки, ссылки, формы и подписи всегда живые. Скриншот с нарисованным
   интерфейсом не является реализацией экрана.

### Отдельные правила платформ

Web: настоящие URL, Back/Forward, deep links, keyboard focus, desktop hover.
Ориентир ширины учебной оболочки 1080px; широкая сцена может быть отдельной.
Desktop-урок с текстом и схемой рядом примерно от 1000px; sticky только при
достаточной высоте. На узком экране схема и объяснение идут последовательно.
Не копировать нижние native-табы в desktop-шапку буквально.

Native: safe area, системная клавиатура, аппаратный Back на Android, Dynamic Type,
VoiceOver/TalkBack. Bottom CTA не перекрывает текст, клавиатуру и вкладки.
Пять вкладок: Главная, Обучение, Практика, Гонка, Меню. Не выделять центр
гигантской плавающей кнопкой. При управлении лодкой/экзамене лишнюю оболочку
скрывать по существующим правилам, но оставлять понятный выход.

Глобальная кнопка называется «Меню», заголовок страницы может быть «Все разделы».
Не называть весь каталог «Библиотека» или «Справочник». Не добавлять вторую
одинаковую кнопку в native-шапку, когда доступна нижняя вкладка.
Старые `/library` ссылки сохранить как совместимый переход к `/menu`.

## 6. Этапы реализации и приёмка

### A0. Инвентаризация и baseline

Прочитать материалы, запустить существующие поверхности, собрать матрицу
маршрутов и текущие скриншоты web/native. Отметить: working, partial, missing,
online-only. Проверить доступные runtime и устройства. Не объявлять Expo web
проверкой iOS. Если native-запуск недоступен, явно указать этот пробел.

Результат: список реально изменяемых файлов, известные регрессии до изменений,
порядок A1-A6 и перечень недостающих изображений. Список первичных приоритетов:
главная, Меню, каталог обучения, один настоящий урок, вход/возврат из практики.

### A1. Компоненты, тема и навигационная оболочка

Уточнить семантические токены, доработать существующие Button, ListRow, Screen,
Text, состояния загрузки/ошибки, заголовки и навигацию. Не создавать параллельную
дизайн-систему для каждой страницы. Светлую native-тему интегрировать через
существующие настройки; если инфраструктуры ещё нет, сначала сделать небольшой
проверяемый слой темы и мигрировать срезами, сохранив fallback старых экранов.

Собрать web-header, native-tabs, полное Меню с поиском и группами: обучение,
экзамены, практика, гонки, на борту/справочные материалы, помощь/настройки.
Каждое публичное назначение каталога появляется один раз на своей платформе.
Не добавлять admin, API или review-маршруты в пользовательское меню.

Приёмка: /menu доступно с главной без прокрутки; поиск, очистка и отсутствие
результатов работают; вложенные маршруты подсвечивают правильного родителя;
пользователь не попадает в тупик. Реальные offline-возможности не определять
по одному устаревшему boolean в каталоге, проверить фактическую реализацию.

### A2. Главная и выбор обучения

Одна главная кнопка: начать для нового пользователя, продолжить для вернувшегося.
Сначала загружать сохранения, не мигать ложным «Начать заново».
На телефоне компактное изображение не должно вытеснять основной сценарий;
на desktop допустима более широкая композиция и соседний список направлений.
Путь курса: названия уроков, понятные состояния и следующий шаг.
Другие курсы доступны, но не конкурируют десятком равнозначных CTA.

Состояния: нет прогресса, частичный, завершённый, загрузка, ошибка чтения,
неизвестный/устаревший ID урока. Никаких фиктивных 3/7, часов, сертификатов
и процентов навыка. Не добавлять обязательный аккаунт или onboarding-опрос
перед доступом к уже существующим материалам.

Приёмка: сохранения старого пользователя не потеряны, курсы открываются по
реальным маршрутам, понятный выбор при завершении курса, перезапуск сохраняет
продолжение. Счётчики вычисляются из действительных данных.

### A3. Один эталонный production-урок

Выбрать существующий урок о гика-шкоте в курсе парусов и подтвердить его ID
по данным. Если его содержание требует изменения вне редизайна, отметить это
отдельно, не сочинять новую экзаменационную истину ради совпадения макета.

Структура: цель -> объяснение «почему» -> схема -> жизненный пример/ошибка ->
проверка понимания -> подходящая практика -> результат и следующий шаг.
Понятия фал, шкот и оттяжка не смешивать. Неверный ответ даёт объяснение,
а не зелёный успех; можно повторить. Теоретический ответ не выдаёт сертификат
и не доказывает практический навык.

Схемы рисовать программно, подписи локализовать, обеспечить клавиатурную
альтернативу drag. Для схемы иметь текстовое объяснение того же смысла.
На native использовать существующий SVG/Skia-подход, не заменять всё PNG.

Приёмка: урок полностью проходит на обеих платформах, проверка действительно
проверяет, состояние шага восстанавливается, диаграмма читается на узком экране,
неверный ответ/возврат/перезапуск не теряют контекст.

### A4. Связь с существующей практикой

Доработать экран выбора практики и краткую инструкцию перед упражнением:
цель, действия, наблюдаемый результат, доступность без сети.
Не переписывать физику и не добавлять новый игровой движок.

Зафиксировать минимальный контракт запуска и возврата поверх существующей
реализации: lessonId, stepId, exerciseId, версия сценария/условий, разрешённый
маршрут возврата. Точные имена полей выбрать после чтения текущих типов.
Результат различает started, exited, failed, passed; открытие экрана не равно
успеху. Повторная доставка результата не должна удваивать прогресс.
Не принимать произвольный return URL или сообщение WebView за доверенный результат.

Не требуется прямо сейчас общий движок сессии или новый backend. Если bridge
нужно менять, это отдельная security-sensitive часть: схема сообщений,
проверка источника/сессии, тесты и соответствующие правила безопасности.

Приёмка: урок -> упражнение -> выход/результат -> тот же урок и шаг.
Проверить обычный выход, Back, reload/перезапуск, неверные параметры ссылки,
повторный результат, офлайн. Смена вида камеры не сбрасывает учебную попытку.

### A5. Тиражирование на существующие разделы

Только после проверки A3 переносить принципы на остальной учебный интерфейс.
Очередь: парусный начальный курс и работа с парусами; словарь/анатомия/чек-листы;
входы и оболочка радио/SRC и моторного курса; существующие гонки, места,
настройки и вспомогательные экраны.

У каждого раздела свои особые задачи. Не превращать экзамен, рацию и гонку
в одинаковую страницу с большой фотографией. В радио сохранить компоновку
модели и реальные клавиши/сигналы/сценарии; менять понятность оболочки, не
незаметно менять процедуры. Устройство яхты не обещает AR, если AR не реализован.

Итогом должна быть матрица всех публичных назначений из каталога и статусов
по платформам. Скрытая недоделанная страница не считается переделанной.
Все работающие возможности остаются доступными. Новые социальные функции,
достижения, реальные карты и платные сервисы не добавлять из картинок автоматически.

### A6. Офлайн, доступность, локализация и регрессия

Проверять постепенно в каждом срезе и повторить общей приёмкой:

- Холодный запуск native в авиарежиме после установки с комплектными материалами;
  отдельно загруженный пакет, отсутствующий пакет и незавершённая загрузка,
  если такие состояния поддерживает существующая система.
- Текст, схемы, новые изображения и обещанные упражнения доступны локально.
  AI-разговоры/сетевые ответы и live-сервисы честно помечены как требующие сети.
- Перезапуск приложения и обновление не стирают локальные сохранения.
- Web-кеш и native-bundle не считать одной и той же гарантией офлайна.
- RU/EN/PL/ES/FR/DE/IT: новые строки через текущую систему, без русских утечек,
  обрезания длинных немецких/польских подписей или текста, запечённого в фото.
- Web 320, 390, 768, 1440px, плюс малая высота/landscape; zoom 200%, keyboard,
  visible focus, reduced motion. Контраст текста AA, состояние не только цветом.
- iOS/Android: safe areas, клавиатура, Back, крупный текст, screen reader,
  тёмная/светлая тема согласно доступным настройкам.
- Изображения имеют размеры/aspect ratio, не вызывают скачки макета. Не грузить
  полный 3D-мир на главной. Проверить прокрутку и отзывчивость на устройстве.

Блокирующие дефекты: потеря данных/контекста, недоступное основное действие,
сломанный маршрут, неверный успех, ложный офлайн, серьёзная ошибка безопасности
или учебной процедуры. Косметические недочёты перечислять, не прятать в «готово».

## 10. Проверки и команды

Команды ниже проверены по package.json, но результаты этого handoff не означают
их новое успешное выполнение. Запускать из корня, если не указано иначе.
Сначала проверить существующий процесс на 3118, не завершать чужой сервер.

```sh
npm run dev -- --hostname 127.0.0.1 --port 3118
```

Если порт занят другим проектом, выбрать свободный и сообщить фактический URL.
Review: http://localhost:3118/design-v3, production-маршруты проверять отдельно.

Проверки web после соответствующего среза:

```sh
npx tsc --noEmit
npx vitest run src/lib/product/catalog.test.ts src/lib/product/learning.test.ts
npm run build
BASE_URL=http://127.0.0.1:3118 npx playwright test e2e/smoke.spec.ts e2e/sailing-learning.spec.ts
```

ESLint запускать по изменённым TS/TSX через существующий `npm run lint -- ...`.
Перед широкой приёмкой запустить полный релевантный suite, не только эти smoke.
Важно: `playwright.config.ts` без BASE_URL смотрит на production. Не запускать
так локальные сценарии случайно. Для проверок с сохранениями использовать
тестовый профиль и синтетические данные, не очищать настоящий прогресс пользователя.

Native:

```sh
npm --prefix mobile run typecheck
npm --prefix mobile run lint
npm --prefix mobile test -- --runInBand
```

Если менялись bundle-входы офлайна, пересобрать соответствующим build-скриптом,
проверить diff и выполнить:

```sh
npm run build:radio-offline:check
npm run build:sailing-offline:check
npm --prefix mobile run sync-content:check
```

Generated HTML не редактировать вручную. `npm --prefix mobile run check` является
сводной проверкой. При изменении физических входов дополнительно выполнить
`npm run test:physics`. Доступные native-команды: `npm --prefix mobile start`,
`npm --prefix mobile run ios`, `npm --prefix mobile run android`; запуск требует
соответствующего локального SDK и может создавать build-артефакты.

Browser-скриншот не проверяет нативную установку, safe area и офлайн-бандл.
Перед выпуском нужен native build и проверка установки/обновления.
Если проверка не выполнена, указать «не проверено», а не «должно работать».
